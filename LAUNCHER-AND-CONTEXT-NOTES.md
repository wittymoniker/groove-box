# Launcher and Context Revision Notes

This revision keeps the first archive's working GUI and wide, independently
scrollable composition and playback canvases. The comparison main windows are
not replacements for that interface. It is a source revision, not a compiled
EXE or ISO, and does not certify a particular laptop.

## Launchers and dependency handling

- **Shared startup:** `run_hybrid.sh` enters the project directory, quotes the
  chosen interpreter, consumes installer-only flags, and enters the compatibility
  launcher. Linux, macOS, desktop, mobile-helper and START wrappers follow that
  path where applicable; Windows retains its platform-specific wrapper.
- **Python selection:** Existing virtual-environment invocation paths are kept
  rather than resolved through symlinks to the base interpreter. Child processes
  discard inherited Python path/home overrides. Fedora's quoted OS identifiers
  are parsed correctly, and system Qt is reused only with its matching Python.
- **Optional native components:** Existing libraries can be reused.
  `GROOVEBOX_REBUILD_NATIVE=1` requests a rebuild. Optional native failure is
  reported without pretending that a platform-specific library was built.
- **Dependency checks:** Required imports are distinct from optional WebEngine.
  The shared runner does not call obsolete installer flags or expect an obsolete
  interpreter marker. Optional WebEngine diagnostics use a bounded child process.
  The appliance path does not invoke a desktop package installer.
- **Relaunch behavior:** Original application arguments survive a relaunch.
  Signal-crash retry does not turn ordinary failures or Ctrl+C into a restart
  loop. Windows command and interpreter paths are quoted separately.
- **ISO runtime staging:** The final stamper explicitly includes
  `scripts/runtime_dependencies.py`, the launcher declaration module. Root
  Python-module synchronization alone does not copy the ancillary `scripts/`
  files. The stamper requires that declaration file in the final rootfs.

## Help, features and contexts

`ReadmeGuideDialog.HELP_TEXT` in `groovebox.py` is the in-application guide.
`HELP_TEXT.md` is extracted from that string rather than maintained as a separate
feature list. The Help dialog offers a search field, Find next, Enter, and
Ctrl+F/Cmd+F. Current sections describe navigation, wider editors, compatible
merged controls, Live Global DJ effects, live recording, pooling and scheduling,
launchers, packaging, diagnostics, and practical boundaries. The HF15 deployment
and diagnostic guidance remains inside the actual help string.

Finite sampled waveform data is not limited to the oscillator preset list when
a supported import/processing path accepts its representation. This does not
mean every waveform is generated by the seed grammar, every file codec is
supported, or arbitrary audio automatically acquires meaningful visual/game
semantics. Each context has its own adapter and schema. RAM, CPU/GPU, sample
format, duration, supported imports and backend availability impose real limits.

The program is streamlined in several hot paths but not globally minimal. Rich
Qt editors, optional media/network/game facilities, compatibility layers and
legacy GUI-owned canonical commits remain. Cooperative canonical batching is
still off by default; this revision does not promise that canonical activation
can never stall the UI.

## Generated-spec ISO repair

The subsequently supplied traceback exposed a missed source-verifier read of
`build_executable/spec/MathematiciansGroovebox.spec`. ISO checks now use a shared
source inventory, and BUILD_KIT uses the same inventory for PyInstaller hidden
imports. The verifier structurally checks that wiring instead of requiring a
previous EXE build. It retains the seven feature/source/overlay checks.
See `ISO-SPEC-DEPENDENCY-REPAIR.md` for the small repair archive's instructions.

## Review boundary

Source inspection and packaging were performed. No application, verifier suite,
EXE build, ISO build or hardware test was run for this revision, as requested.
The small comparison pass concentrated on the current launch/help/context paths
and compatible existing modules; it is not a claim that every possible feature
from both comparison archives was merged.
